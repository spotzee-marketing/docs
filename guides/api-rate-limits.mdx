The Spotzee API enforces per-source-IP rate limits at the edge today. Two rules apply across `apix.spotzee.com`.

| Rule | Surface | Limit | Action | Block duration |
|---|---|---|---|---|
| Client API limit | `/api/client/*` | 8,000 requests per minute per IP | Block (HTTP 429) | 120 seconds |
| General API limit | `/api/*` (covers `/api/client/*`, `/api/admin/*`, `/api/ext/*`) | 4,000 requests per 10 seconds per IP | Block (HTTP 429) | 10 seconds |

Requests to `/api/client/*` count towards both limits. Either rule can block an IP, depending on its traffic. Both rules count matching requests from each source IP, authenticated or not.

## Event list reads

`GET /api/client/events` has a budget of 6,000 requests per project secret API key in a 60-second rolling window. Pulls using the same key share this budget, even when they come from different IPs.

The event list response reports the budget as `X-RateLimit-Limit`, the remaining requests as `X-RateLimit-Remaining` and the estimated seconds until the window clears as `X-RateLimit-Reset`. When the key reaches its budget, the API returns `429` with code `rate_limited` and a `Retry-After` header in seconds. For paging and resuming a bulk pull, see [Query events](/guides/query-events#pull-events-in-bulk).

## Response on a block

Over-limit requests receive `429 Too Many Requests` with this JSON body:

```http
HTTP/1.1 429 Too Many Requests
```

```json
{
  "status": "error",
  "code": "rate_limited",
  "title": "Rate limit exceeded",
  "message": "Rate limit exceeded. Slow down and retry after the period in `Retry-After`.",
  "type": "https://docs.spotzee.com/main-api/errors#rate_limited"
}
```

## Retry strategy

<Steps>
  <Step title="Honour Retry-After when present">
    If the response includes `Retry-After`, wait at least that long before retrying. Otherwise, use exponential backoff. Another request can still receive `429` while a block remains active.
  </Step>
  <Step title="Add jitter when fanning out">
    If you're driving many requests in parallel from a single host, add 0–500 ms of jitter on top of your delay so retries don't synchronise.
  </Step>
  <Step title="Back off on repeats">
    If you see a second `429`, honour `Retry-After` when present. Otherwise, double your delay (exponential backoff) up to a sensible cap, for example 60 seconds.
  </Step>
  <Step title="Cap concurrency per IP">
    Pace outbound traffic from each source IP. For event lists, also pace jobs that share a project key.
  </Step>
</Steps>

## Self-throttling example

```javascript
async function readApi(path, token) {
  for (let attempt = 0; attempt < 3; attempt++) {
    const response = await fetch(`https://apix.spotzee.com/api/client${path}`, {
      headers: { Authorization: `Bearer ${token}` }
    })
    if (response.status !== 429 || attempt === 2) return response
    const header = response.headers.get('Retry-After')
    const seconds = Number(header)
    const wait = header && Number.isFinite(seconds)
      ? seconds * 1000
      : Date.parse(header ?? '') - Date.now()
    const delay = Number.isFinite(wait) ? Math.max(0, wait) : 1000 * 2 ** attempt
    await new Promise(resolve => setTimeout(resolve, delay + Math.random() * 500))
  }
}
```

## Quota-metered endpoints

The Extended API meters certain operations separately from request rate limits. Insufficient credits can return `402` even when request capacity remains available. Check your balance in the Spotzee app before high-volume runs; no public Quota endpoint appears in the generated Extended API reference.

## Rolling out

For other routes, per-key read/write budgets, `X-RateLimit-*` headers and a doubled MCP budget depend on rollout availability. Stay within the per-IP limits regardless of the client-type header. Honour `Retry-After` when present and use jitter and exponential backoff on either layer.
