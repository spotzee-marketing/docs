A **journey** is a graph of steps that users move through. Use journeys for onboarding sequences, abandonment recovery, renewal reminders, lifecycle re-engagement, and any multi-step automation. Users enter at an `entrance` node and progress until they hit an `exit` or the graph ends.

## How users enter

An `entrance` node has one of three modes:

- **`event`**: a user enters when a tracked event occurs (e.g. `purchase_made`, `form_submitted`).
- **`schedule`**: the journey runs on a recurring schedule against a segment.
- **`none`**: entries come from the API or another journey, not from a trigger condition.

A journey can have multiple entrance nodes for the same flow (e.g. one entrance per signup source).

## Control repeat entries

Schedule frequency controls when the entrance checks its segment. Use **Multiple Entries** to control repeat entry.

With **Multiple Entries** off, the same contact record can enter each entrance only once, even if the contact completes the journey and the schedule checks the segment again on a later day. Turn it on to allow re-entry after a run ends.

To allow a contact to enter that entrance while an earlier run is still active, turn on **Simultaneous Entries**, which appears only when **Multiple Entries** is on. Changing the schedule preserves both entry settings.

## Set schedule dates and times

Schedule dates and times follow the project's timezone. Choose **On Date** for a run that happens once, or set a **Start Date** for a recurring schedule.

Recurring schedules accept hours from **0** to **23**. Use **0** for midnight. Choosing an **End Date** includes the whole final day, so a run at the selected hour can still occur on that date.

## Step types

| Step | Purpose |
|---|---|
| `action` | Send a campaign through its configured provider |
| `delay` | Wait a fixed duration, until a specific time, or for a templated date |
| `gate` | Conditional split based on user attributes or behaviour |
| `experiment` | Weighted random A/B/n split |
| `balancer` | Random distribution across children with per-child rate limits |
| `throttle` | Hold users in a single-path queue until the next rate-limit window opens |
| `link` | Hand the user off to another journey |
| `update` | Patch user attributes using template variables |
| `event` | Emit a tracked event for the user |
| `exit` | Force-remove the user from another entrance |
| `sticky` | Operator-facing canvas note. No runtime effect. |

## Build a journey

<Steps>
  <Step title="Pick an entrance">
    Choose **event** for behaviour-driven journeys, **schedule** for recurring sweeps, or **none** for journeys triggered from the API or another journey.
  </Step>
  <Step title="Add an action step">
    Select a campaign with the channel and template you want. The template can pull user attributes and event data via merge tags.
  </Step>
  <Step title="Add branching where needed">
    Use `gate` to send different content to different cohorts. Use `experiment` to test variants.
  </Step>
  <Step title="Add delays and exits">
    Pace the journey with `delay` steps and remove ineligible users with `exit`.
  </Step>
  <Step title="Activate">
    Toggle to **live**. Spotzee starts evaluating entrances immediately.
  </Step>
</Steps>
