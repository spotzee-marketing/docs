Use a domain blacklist check to inspect the configured domain lists before investigating a delivery problem. A listing is one signal; it does not establish how every mailbox provider will handle your messages.

## Check a domain

<Steps>
  <Step title="Enter the domain">
    Enter a bare domain such as `example.com`. The API expects a `domain` field, not a full email address.
  </Step>
  <Step title="Choose the scan">
    Use `popular` for the smaller configured set or `full` for all configured domain lists. The API defaults to `full`.
  </Step>
  <Step title="Inspect individual results">
    Read `data.check_results` alongside the `listed`, `unlisted` and `errors` totals in `data.results`. Each result names the list and reports `Listed`, `Unlisted` or `Error`.
  </Step>
  <Step title="Confirm and investigate a listing">
    Check the named list operator's current guidance. Investigate the cause before requesting removal; this tool does not submit a delisting request.
  </Step>
</Steps>

## Interpret incomplete evidence

An `Error` means a check could not complete. An `Unlisted` result means the tool did not recognise a listing response. Some refused or unexpected DNS responses can also appear as `Unlisted`, so an all-clear result is not proof that every list accepted the query.

The current domain check rejects some valid long domain suffixes. If a valid domain is rejected, use the list operator's own lookup rather than treating the validation error as a reputation verdict.

For delivery troubleshooting, also inspect the [sending IP](/guides/tools/blacklist-security/ip-blacklist-check) and [email authentication](/guides/tools/email-validation/email-health-check). Domain and IP listings are separate checks.
